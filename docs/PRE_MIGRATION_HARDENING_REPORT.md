# PRE-MIGRATION HARDENING REPORT

**المشروع:** License Archive – Migration Lab  
**النطاق:** تحصين داخلي للمختبر فقط قبل أي نقل مستقبلي إلى Supabase PostgreSQL وCloudflare Pages.  
**حدود التنفيذ الملتزم بها:** لم يُنشأ Supabase، ولم يُربط Cloudflare أو DNS أو النطاق الحالي، ولم تُنقل أي بيانات Production، ولم تُلمس Production أو نسخة Development. استُخدمت بيانات اختبارية داخل المختبر فقط.

> **الحالة:** اكتملت مرحلة التحصين المطلوبة للمختبر. ما زال النقل نفسه مؤجلاً ويستلزم موافقة مستقلة لاحقة.

## 1. المشاكل التي تم إصلاحها

| المجال | التحصين المنفذ |
|---|---|
| صيغة رقم الأرشفة | استبدلت الصيغة السابقة بالحرف الأول بصيغة إلزامية: `آخر 4 أرقام-تسلسل رباعي-لاحقة النوع`. |
| فرادة الرقم | أضيف `UNIQUE` إلى `licenses.archiveNumber`، وسجل تاريخ مستقل `archive_number_history` بقيد فريد يمنع إعادة استخدام أي رقم سابق. |
| الحجز الذري | أضيف جدول `archive_sequences` لكل نوع منشأة؛ يحجز الخادم التسلسل داخل معاملة مع قفل `FOR UPDATE` قبل إنشاء الترخيص وسجل التاريخ. |
| الإدخال المتزامن | أصبح كل إنشاء يمر عبر حجز خادمي/قاعدي، ولا يحدد العميل الرقم النهائي. الاختبار المتوازي يثبت ثمانية أرقام صيدليات فريدة. |
| تعديل الرقم | أضيف إجراء `changeArchiveNumber` للمدير فقط، مع سبب إلزامي، والتحقق من الصيغة، ومنع الرقم الحالي والمستخدم تاريخياً، وكتابة حدث وسجل تدقيق. |
| التجديد | أضيف إجراء `renew` إداري لا يقبل رقم أرشفة ولا يغيره. |
| Offline Queue | أضيفت `idempotencyKey` و`fingerprint` و`operation: create`. تمنع البصمة التكرار المحلي، ويعيد الخادم نتيجة السجل نفسه عند إعادة الإرسال بالمفتاح ذاته. |
| فشل الرد | تبقى العملية الفاشلة في Local Storage، وتستأنف بالمفتاح نفسه؛ محاكاة نجاح الخادم ثم انقطاع الرد أثبتت أن الإعادة لا تنشئ سجلاً ثانياً. |
| تعارض Offline | لا يدعم الطابور إلا `create`؛ لا يضع تعديل ترخيص أو تجديد أو تغيير رقم أرشفة في وضع Offline، وبالتالي لا يكتب فوق تعديل أحدث. إعادة استعمال مفتاح لنفس عملية مختلفة مرفوضة بخطأ تعارض. |
| RLS وقابلية النقل | أضيفت وثيقة تصميم مفصلة للسياسات والجداول وRPC وبدائل MySQL وExpress/tRPC وManus. |

## 2. تصميم رقم الأرشفة النهائي

الصيغة النهائية ثابتة في الخادم ومعاينة الواجهة والاختبارات:

| نوع المنشأة | المثال الأول | المثال الثاني |
|---|---|---|
| صيدلية | `6543-0001ص` | `6543-0002ص` |
| مخزن أدوية | `8765-0001م` | `8765-0002م` |

يتحقق الخادم من رقم الترخيص اليدوي، ويستخرج آخر أربع خانات، ويحجز عداداً منفصلاً للصيدلية أو المخزن. يحفظ كل تخصيص في `archive_number_history` ولا يسمح بإعادة استعمال الرقم حتى لو تغير أو حُذف السجل التشغيلي لاحقاً. ينتج عن فشل إنشاء لاحق فجوة محتملة في العداد، وهي مقبولة ومقصودة لحماية عدم إعادة الاستخدام.

## 3. تصميم Offline Queue

يحفظ الطابور عنصر إنشاء فقط يحتوي على معرف محلي ومفتاح idempotency وبصمة `facilityType + licenseNo` وبيانات النموذج. لا يحذف العنصر عند خطأ الشبكة؛ يضيف وصف الخطأ ويحتفظ بالمفتاح نفسه. عند عودة الاتصال، يرسل مدير المزامنة المفتاح نفسه إلى `licenses.create`.

يحفظ الخادم المفتاح وبصمة الحمولة في `idempotency_requests`. إذا انقطع الرد بعد نجاح الحفظ ثم استأنف العميل المزامنة، يعيد الخادم المعرف السابق مع `idempotent: true` بدلاً من إنشاء سجل جديد. إذا حاول عميل استعمال المفتاح نفسه لحمولة مختلفة، يرفضه الخادم. وقد اختبر ذلك بعد إعادة قراءة الطابور من Local Storage وإعادة تحميل وحدة الراوتر وإنشاء caller جديد.

> العمليات غير المدعومة Offline عمداً هي التعديل والتجديد وتغيير رقم الأرشفة والأرشفة. تظل هذه عمليات متصلة، محمية بالصلاحيات، وتمنع الكتابة فوق تعديل أحدث.

## 4. تصميم RLS وصلاحيات Supabase المستقبلي

أضيف الملف [`PRE_MIGRATION_RLS_AND_PORTABILITY.md`](./PRE_MIGRATION_RLS_AND_PORTABILITY.md) لتوثيق التصميم دون إنشاء مشروع Supabase. يحدد وثيقة `app_profiles` المرتبطة بـSupabase Auth، والأدوار `admin` و`archivist` و`user`، وحالات `pending` و`approved` و`blocked`.

| القدرة المستهدفة | المدير | موظف الأرشيف | المستخدم العادي |
|---|---:|---:|---:|
| عرض السجل | نعم | نعم | لا |
| إدخال ترخيص | نعم | نعم | لا |
| تعديل بيانات الترخيص | نعم | لا | لا |
| تعديل رقم الأرشفة | نعم عبر RPC فقط | لا | لا |
| سجل التدقيق الكامل وإدارة المستخدمين | نعم | لا | لا |

تفرض الخطة RLS على كل جدول مكشوف، وتحجب `anon` من جداول الأعمال، وتبقي `service_role` في جهة الخادم فقط. وتوصي بوظائف PostgreSQL/RPC ذرية لإنشاء الترخيص وتعديل الرقم والتجديد، مع اختبارات RLS للحالات المسموحة والمرفوضة [1].

## 5. الاعتمادات المفصولة أو الموثقة للنقل

| الاعتماد | وضع التحصين الحالي | ما يلزم لاحقاً |
|---|---|---|
| MySQL / Drizzle | أضيفت قيود وسجل تسلسل في المختبر، ووثقت مواضع `mysql-core` و`mysql2` و`insertId` و`onDuplicateKeyUpdate`. | تحويل المخطط إلى `pg-core` أو SQL PostgreSQL واستخدام `RETURNING`/RPC في مشروع Supabase Test. |
| Express / tRPC | لم يحذف أي منهما، ووثقت طبقات `server/_core` والسياق والجلسات. | محول Fetch/Workers أو Supabase RPC عند الانتقال إلى Pages Functions؛ لا يعمل خادم Express الحالي كما هو في Pages. [2] |
| Manus OAuth | لم يغير في هذه المرحلة. | استبداله بـSupabase Auth وJWT وسجل أدوار جديد لاحقاً. |
| Manus Storage / المرفقات | لم يضف File Storage أو مرفقات. | يبقى خارج نطاق النقل؛ مسارات أصول طباعة الوزارة الحالية تحتاج مصدراً ثابتاً معتمداً قبل النقل. |
| AI | لم يضف AI أو LLM. | يبقى اختبار Zero-AI حارساً لمسارات الإدخال والحفظ والتعديل والبحث والأرشفة والطباعة/PDF وCSV والتقارير. |

## 7. بيانات الاختبار

لم تُستخدم بيانات Production. أنشأت الاختبارات سجلات تحمل تسميات اختبارية مثل `OFF-*` و`CON-*` و`ARCHIVE-*` وتنتهي أرقام تراخيصها بـ`6543` أو `8765` للتحقق من الصيغة. تبقى هذه بيانات مختبر فقط، ويحتفظ سجل تاريخ الأرشفة بها عمداً لإثبات عدم إعادة الاستخدام.

## 8. الحالة الأمنية والمشكلات المتبقية

لا تزال نتيجة `pnpm audit --prod` غير نظيفة: **81 ملاحظة**، منها 1 حرجة و21 عالية و49 متوسطة و10 منخفضة. لم تُحدّث تبعيات في هذه المرحلة لتجنب تغيير غير منضبط خارج هدف التحصين؛ يجب تنفيذ برنامج تحديث منفصل قبل أي نشر خارجي.

كما يبقى تحذير حجم حزمة Vite الرئيسية فوق 500 كيلوبايت بعد التصغير. لا يمنع التحصين الوظيفي، لكنه يستلزم تقسيم PDF والمعايرة والمسارات النادرة قبل تحسين تجربة Cloudflare Pages على الجوال.

لا تزال هذه العناصر **خارج نطاق المرحلة الحالية**: إنشاء Supabase، ترحيل PostgreSQL، تنفيذ RLS الفعلي، استبدال OAuth، ربط Cloudflare Pages، DNS، النطاق، نقل البيانات الحقيقية، وإعادة تصميم أصول نموذج الوزارة خارج `/manus-storage`.

## 9. القرار والخطوة التالية

المختبر محصن وظيفياً لاختبار Migration لاحق، لكنه لا يزال يعمل على البنية الحالية. الخطوة التالية لا تبدأ إلا بموافقة مكتوبة مستقلة لإنشاء **Supabase Development/Test** فارغ، ثم تنفيذ مخطط PostgreSQL وRLS وRPC وفق الوثيقة، باستخدام بيانات اختبارية فقط.
