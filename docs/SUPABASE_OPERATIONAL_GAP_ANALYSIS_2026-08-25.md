# تحليل فجوات التحويل التشغيلي إلى Supabase Development

**التاريخ:** 25 أغسطس 2026  
**النطاق:** مقارنة مخطط MySQL وtRPC المحليين مع مشروع `License Archive – Migration Lab (Development)` ذي المعرف `qduofealtaikxhhrjxly`. لا يتضمن هذا التحليل Production أو بيانات حقيقية أو نشر أو DNS أو Cloudflare.

## خلاصة القرار

يمتلك Supabase Development بالفعل النواة الأمنية الصحيحة لتراخيص المختبر: `app_profiles` المرتبط بـSupabase Auth، وجدول `licenses`، وسجل تاريخ أرقام الأرشفة، وتسلسل محمي في مخطط `private`، وطلبات idempotency، والأحداث، وسجل التدقيق. كما توجد إجراءات RPC للتحقق من الدور، وإنشاء السجل، والتجديد، وتعديل رقم الأرشفة، والأرشفة، والتعديل، والحذف الناعم، والاستعادة.

لكن المسار التشغيلي الرئيسي ما زال يعتمد على `licenses` في tRPC/MySQL. والفجوة المباشرة ليست حذف هذا المسار، بل توسيع مخطط Supabase ليغطي الحقول التشغيلية الناقصة، ثم تقديم طبقة قراءة متوافقة مع الصفحة الحالية تتضمن بحثاً وفلترة وترتيباً وتقسيماً إلى صفحات من جهة قاعدة البيانات.

> **لا ينفذ هذا التحليل أي حذف أو نقل بيانات أو تغيير لمسار MySQL/tRPC.** يبقى المسار الحالي بديلاً تشغيلياً حتى اجتياز كل مراحل التوافق داخل Development.

## 1. مقارنة الجداول

| الكيان | MySQL الحالي | Supabase Development | قرار المرحلة الحالية |
|---|---|---|---|
| المستخدمون | `users` مع الدور وحالة الوصول وبيانات دخول Manus | `app_profiles` مرتبط بـ`auth.users` مع الدور وحالة الوصول | متوافق للهوية والأدوار؛ تختلف هوية المستخدم من رقم صحيح إلى UUID، وهذا مقصود. تبقى حقول دخول Manus ضمن المسار القديم حتى اكتمال تبديل المصادقة. |
| التراخيص | `licenses` كامل بالحقول التشغيلية والطباعة والاستلام | `public.licenses` يغطي البيانات الأساسية والأرشفة والحذف الناعم | يحتاج أربعة حقول تعليمية وثلاثة حقول استلام وطريقة تحديث RPC موسعة. |
| تسلسل الأرشفة | `archive_sequences` | `private.archive_sequences` | متوافق، مع قفل/رفع حد التسلسل داخل RPC. |
| تاريخ أرقام الأرشفة | `archive_number_history` | `public.archive_number_history` | متوافق؛ فريد وغير قابل للتعديل أو الحذف. |
| Idempotency | `idempotency_requests` | `private.idempotency_requests` | متوافق؛ المفتاح UUID في Supabase بدلاً من نص بطول 64 في MySQL. |
| أحداث الترخيص | `license_events` | `public.license_events` | متوافق تشغيلياً؛ أسماء بعض الأحداث تختلف وتحتاج تثبيت قائمة شاملة متوافقة. |
| سجل التدقيق | `audit_logs` | `public.audit_logs` | متوافق مع `jsonb` بدلاً من النص، وهي تحسين مناسب لـPostgreSQL. |
| التنبيهات | `notifications` | غير موجود | مؤجل؛ يعتمد على قرار واضح حول job/Heartbeat ولا يدخل ضمن أول شريحة نقل قراءة/CRUD. |
| المستندات | `documents` مع S3 metadata | غير موجود | مؤجل عمداً: لا تُنشأ Storage أو مرفقات في هذه المرحلة وفق القيود المعتمدة. |

## 2. فجوات أعمدة التراخيص

| المجموعة | أعمدة موجودة في MySQL وغير موجودة في Supabase | أثر الفجوة | الإجراء الآمن |
|---|---|---|---|
| بيانات المؤهل | `graduation_place`, `graduation_institution_type`, `graduation_date` | فقدان توافق نموذج الإدخال/التعديل والطباعة مع البيانات الحالية | إضافة أعمدة nullable وقيود تحقق قائمة القيم حيث يلزم، ثم السماح بها في RPC التحديث. |
| استلام الترخيص | `license_delivery_recipient_name`, `license_delivery_signature`, `license_delivery_fingerprint` | عدم تطابق بيانات الاستلام في التفاصيل والطباعة الرسمية | إضافة أعمدة nullable وضمها إلى RPC التحديث فقط؛ لا تُدخل صوراً أو File Storage. |
| تحققات زمنية | لا يوجد قيد جدول عام على `expiry_date > issue_date` | قد تظهر قيمة غير صالحة إذا أضيفت دالة جديدة مستقبلاً | إضافة `CHECK` باسم ثابت بعد التحقق من بيانات الاختبار الحالية. |

## 3. الفهارس والقيود

توجد في Supabase فهارس التفرد المطلوبة لرقم الترخيص ورقم الأرشفة، وفهارس الحالة والنوع والمحافظة والانتهاء والإنشاء والحذف الناعم، إضافة إلى فهارس المفاتيح الخارجية وسجلات الأحداث والتدقيق. وتوجد قيود تنسيق رقم الأرشفة والتسلسل وسبب تعديل الرقم. تحتاج واجهة القائمة التشغيلية إلى فهارس مركبة موجهة لاستعلامات القراءة الشائعة، لا إلى تحميل أول 100 صف ثم فلترته في المتصفح.

| الحاجة | الحالة الحالية | التعديل المخطط |
|---|---|---|
| Pagination + ترتيب قائمة التراخيص النشطة | القائمة التجريبية تحمّل حتى 100 صف وتفلتر محلياً | RPC قراءة مرقمة تقبل ترتيباً آمناً وتعيد `items` وبيانات pagination. |
| البحث برقم الترخيص أو الأرشفة أو المنشأة أو المالك | فلترة محلية بعد الجلب | بحث خادمي محدود بمطابقة نصية آمنة في RPC، مع فهارس مناسبة عند تحقق حجم البيانات. |
| فلاتر الحالة والنوع والمحافظة والتاريخ | جزء منها متاح عبر REST للمختبر فقط | نقلها إلى RPC موحد يستعمل شروطاً من جهة PostgreSQL. |
| تاريخ الأرشيف والسلة | قائمة منفصلة محدودة إلى 100 صف | RPC مستقل للائحة الأرشيف والسلة، مع RLS وصلاحية المدير. |

## 4. منطق tRPC غير المنقول بعد

| المجال | حالة Supabase | ملاحظة النقل |
|---|---|---|
| القائمة والبحث والفلاتر والترتيب والتقسيم | جزئي | هذه أول شريحة نقل للصفحات الرئيسية، عبر طبقة توافق لا تغيّر مكونات الواجهة. |
| الإضافة والتعديل والتجديد والأرشفة وتغيير الرقم | موجودة للمختبر | تحتاج توسيع حمولة RPC لتشمل كل الأعمدة، ثم ربط تدريجي بنماذج التطبيق. |
| الحذف الناعم والاستعادة والسلة | موجودة للمختبر | تحتاج عقود قائمة مرقمة وتأكيدات الواجهة الحالية. |
| المستخدمون والفريق | مصادقة وملف ودور موجودة | إدارة الأدوار داخل التطبيق لم تنتقل بعد؛ تظل MySQL/tRPC المصدر التشغيلي إلى حين تصميم إجراءات إدارة آمنة. |
| Audit Log والأحداث | موجودة ومقيدة بـRLS | تعرضها وتشغيل فلاترها من الصفحة التشغيلية لم ينتقلا بعد. |
| Dashboard والإحصائيات | غير منقول | يحتاج RPC إحصاءات مستقل بعد قائمة التراخيص. |
| التصدير والطباعة الرسمية وPDF | غير منقول | يبقى منطق العرض والطباعة الحالي كما هو؛ مصدر البيانات ينتقل لاحقاً فقط بعد اختبار تطابق. |
| التنبيهات والمستندات | غير منقول | مؤجلان صراحةً؛ لا File Storage ولا job جديد ضمن هذه المرحلة. |

## 5. المصادقة وRLS

Supabase Development يدعم جلسات Supabase Auth وملف المستخدم والأدوار `user` و`archivist` و`admin` وحالات الوصول `pending` و`approved` و`blocked`. والتحقق الحاسم موجود داخل دوال RPC عبر الدور وحالة الاعتماد؛ فإخفاء الأزرار ليس أساس الحماية. ما زال التطبيق الرئيسي يستخدم جلسة Manus OAuth عبر tRPC، ولذلك لا يجوز تبديل مصادقة الصفحات الحالية قبل أن توجد طبقة جلسة Supabase متوافقة ومسار رجوع واضح.

## 6. تسلسل التنفيذ المعتمد

تبدأ المرحلة الثانية بنقطة استعادة محلية غير منشورة، ثم Migration واحد آمن يضيف الأعمدة والقيود والفهارس اللازمة إلى **Supabase Development فقط**. بعد ذلك، تبدأ شريحة القراءة من خلال إجراءات RPC مرقمة للائحة والبحث والفلاتر، مع بقاء تفعيل الصفحة الرئيسية خلف مفتاح انتقال Development لا يمس المسار الحالي. لا ينتقل إنشاء أو تعديل أو أرشفة أي صفحة تشغيلية قبل اكتمال اختبارات الشريحة السابقة.

## 7. ما يبقى خارج المرحلة الأولى والثانية

يبقى MySQL وDrizzle وtRPC كما هي، ولا تُنقل البيانات الحقيقية، ولا تُنشأ موارد Cloudflare، ولا يُغير DNS أو Domain. كما لا تنشأ Storage أو جداول مرفقات أو مسار مزامنة بيانات Production. لا يُعد هذا التقرير تصريحاً للنشر أو ترحيل Production.
