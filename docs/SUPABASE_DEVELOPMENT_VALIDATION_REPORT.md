# SUPABASE DEVELOPMENT VALIDATION REPORT

**المشروع:** License Archive – Migration Lab (Development)  
**النطاق:** Supabase Development مستقل فقط، في منطقة `ap-northeast-2`  
**حالة المرحلة:** مكتملة للتحقق الخلفي وقاعدة البيانات؛ لا يوجد Migration حقيقي ولا نشر خارجي.  
**إعداد التقرير:** 22 أغسطس 2026

## 1. ملخص تنفيذي

تم إنشاء مشروع Supabase Development منفصل وفارغ لمختبر النقل، ثم تطبيق مخطط PostgreSQL المعتمد وسياسات RLS ودوال RPC المحمية ومشغلات التدقيق والتحصين. اقتصر المحتوى على حسابات وسجلات اختبارية تحمل نطاق `example.test`، ولم يُنسخ أو يُدخل أي سجل من Production.

تم التحقق من إنشاء الترخيص، والبحث، والتجديد، والأرشفة، وتعديل رقم الأرشفة للمدير، ورفض المستخدم العادي والحساب المحظور، وسجل التدقيق، ومنع التكرار وإعادة الاستخدام، وIdempotency، وRLS. نجحت اختبارات المشروع المحلية كذلك: **94 اختبار Vitest**، وفحص TypeScript، وبناء الإنتاج.

> لم يتم إنشاء أو تغيير Cloudflare Pages أو DNS أو النطاق أو الموقع الحالي. كما لم يُربط مشروع Supabase هذا بأي بيانات أو حسابات Production.

| البند | النتيجة |
|---|---|
| مشروع Supabase Development مستقل | **ناجح** |
| نقل بيانات Production | **لم يحدث** |
| File Storage أو مرفقات أو جدول مستندات | **غير منشأ** |
| RLS على جداول الأعمال والداخلية | **مفعّل** |
| العمليات اليومية عبر AI | **غير موجودة في مسار المختبر** |
| Cloudflare / DNS / Domain | **لم يُعدّل** |

## 2. البنية المطبقة

يتكون المخطط من جداول `app_profiles` و`licenses` و`archive_number_history` و`license_events` و`audit_logs`، وجداول داخلية في مخطط `private` للعدادات ومفاتيح Idempotency. تم استبعاد جدول `documents` وأي Storage أو مسارات مرفقات عمداً.

| المكوّن | الضبط المطبق |
|---|---|
| الأدوار | `admin` و`archivist` و`user` مع حالات `approved` و`pending` و`blocked`. |
| الأرشفة | رقم يُولَّد خادمياً وفق آخر 4 أرقام من رقم الترخيص ثم تسلسل رباعي ولاحقة `ص` أو `م`. |
| سجل التاريخ | `archive_number_history` فريد وAppend-only لمنع إعادة استخدام أي رقم سابق. |
| التدقيق | `audit_logs` و`license_events` يسجلان الإنشاء والتجديد والأرشفة وتغيير رقم الأرشفة. |
| Idempotency | `idempotency_key` مع بصمة حمولة، يعيد النتيجة الأصلية عند الإرسال نفسه ويرفض المفتاح نفسه مع حمولة مختلفة. |
| مشغلات الحماية | تحديث `updated_at`، وإنشاء ملف مستخدم عند Auth، ومنع تحديث/حذف سجلات التاريخ والتدقيق. |

طبقت ستة ترحيلات مرتبة: المخطط الأساسي، وتفعيل RLS الداخلي، وتصحيح دالتي تغيير رقم الأرشفة والتجديد، وتحجيم تعرّض دالة Auth الداخلية، وسياسات الرفض الصريح للجداول الداخلية، ثم فهارس المفاتيح الخارجية.

## 3. RLS والصلاحيات

تُمنح أقل الصلاحيات اللازمة، ثم تحدد RLS الصفوف القابلة للقراءة. يُمنع الإدخال والتعديل المباشر على جداول الأعمال؛ العمليات الحساسة متاحة فقط عبر دوال RPC `SECURITY DEFINER` ذات `search_path` ثابت وفحص داخلي لـ`auth.uid()` والدور وحالة الاعتماد. هذا يتبع مبدأ أن Grants وRLS طبقتان متكاملتان، وأن استدعاء الدوال يجب أن يُقيد صراحةً [1] [2].

| هوية الاختبار | التراخيص المرئية | Audit Log المرئي | النتيجة |
|---|---:|---:|---|
| مستخدم عادي معتمد | 0 | 0 | الرفض صحيح |
| موظف أرشيف معتمد | 4 | 0 | القراءة الصحيحة دون سجل تدقيق |
| مدير معتمد | 4 | 7 | الوصول الإداري الصحيح |
| مستخدم محظور | غير مسموح له بإنشاء ترخيص | غير منطبق | الرفض صحيح |

تم أيضاً اختبار رفض الكتابة المباشرة في `licenses` لحساب موظف الأرشيف، ورفض محاولة المستخدم العادي لتعديل رقم الأرشفة. لا يستطيع عميل خارجي قراءة أو تعديل `private.archive_sequences` أو `private.idempotency_requests`؛ RLS مفعل عليهما مع سياسة رفض صريحة، وتستخدمهما الدوال المحمية فقط.

## 4. التحقق من الأرشفة والعمليات

أدخلت الدالة الخادمية السجلات التجريبية الأربعة المطلوبة رقمياً. كان التسلسل الأولي مطابقاً للتعاقد المعتمد؛ ثم غُيّر الرقم الثاني للصيدلية إدارياً إلى `6543-0003ص` لاختبار السجل ومنع إعادة استخدام `6543-0002ص`.

| الاختبار | النتيجة الموثقة |
|---|---|
| إنشاء صيدلية أولى | `6543-0001ص` |
| إنشاء صيدلية ثانية قبل تعديل المدير | `6543-0002ص` |
| إنشاء مخزن أول | `8765-0001م` |
| إنشاء مخزن ثان | `8765-0002م` |
| تعديل المدير لرقم الصيدلية الثانية | نجح إلى `6543-0003ص` مع سبب إلزامي وسجل تاريخ وتدقيق |
| إعادة استخدام `6543-0002ص` | رُفضت |
| التجديد | نجح وحافظ على رقم الأرشفة الأصلي |
| الأرشفة | نجحت للترخيص التجريبي مع حدث وسجل تدقيق |
| البحث | أعاد سجلات الأرشفة المتوقعة تحت دور موظف الأرشيف |
| Idempotency / Offline→Online | إعادة الإرسال بالمفتاح وبصمة الحمولة نفسيهما أعادت السجل الأصلي فقط؛ الحمولة المختلفة بالمفتاح نفسه رُفضت |

تظهر الأدلة الحالية أربعة تراخيص اختبارية، وخمسة سجلات لتاريخ أرقام الأرشفة (أربعة تخصيصات أولية وتعديل إداري واحد)، وسبعة أحداث تدقيق: أربعة إنشاءات، وتغيير رقم واحد، وتجديد واحد، وأرشفة واحدة.

## 5. Offline/Online وحدود التحقق

تم التحقق من عقد Offline في طبقة قاعدة البيانات: إنشاء فقط مع `idempotency_key` ثابت وبصمة طلب. يحاكي ذلك انقطاع الاستجابة بعد حفظ الخادم ثم إعادة الإرسال عند عودة الاتصال؛ تعيد الدالة النتيجة السابقة بدلاً من إنشاء سجل ثانٍ. كما أن المفتاح نفسه لا يقبل حمولة مختلفة.

لا تنقل هذه المرحلة واجهة PWA الحالية إلى Supabase بعد؛ لذلك فإن إثبات Offline/Online هنا هو **اختبار RPC/قاعدة بيانات** لعقد المزامنة، وليس اختباراً لشاشة Web مستقلة مستضافة خارج Manus. جُرّب كذلك إنشاء حساب Auth تجريبي عبر HTTP، لكن Supabase Auth رفض عناوين الاختبار الاصطناعية؛ لذلك لم يُستخدم حساب شخص حقيقي لتجاوز القيد. يظل اختبار الواجهة HTTP/Offline الفعلي بنداً معلقاً إلى أن تعتمد حساب اختبار أو نطاق بريد تجريبي صريح.

## 6. Zero-AI وعدم استخدام التخزين

أضيف اختبار يمنع إدخال استدعاءات LLM أو توليد صور أو Supabase Storage أو أوامر إنشاء جداول المستندات/المرفقات داخل مسارات `supabase/`. اجتاز الاختبار ضمن مجموعة Vitest. لا تحتوي الدوال اليومية في المخطط على أي مسار AI؛ وهي مقتصرة على PostgreSQL وRLS وRPC.

لم تُغير نصوص نموذج إدخال الترخيص أو نموذج الطباعة الرسمي للوزارة، ولم تُنقل أصول الطباعة أو PDF أو QR إلى Supabase في هذه المرحلة.

## 7. الجودة والأمان

اجتازت الأدوات المحلية فحص TypeScript، و**94 اختبار Vitest**، وبناء الإنتاج. أضيفت فهارس للمفاتيح الخارجية التي رصدها مستشار الأداء. الملاحظات الوحيدة المتبقية من مستشار الأداء هي «فهرس غير مستخدم»؛ وهذا متوقع في قاعدة تطوير جديدة ذات أربعة سجلات اختبارية، ولا يبرر حذف فهارس البحث أو التدقيق المقصودة.

| الملاحظة | الحالة | المعالجة أو القرار |
|---|---|---|
| دالة Auth الداخلية كانت قابلة للاستدعاء | عولجت | أزيل `EXECUTE` عن `anon` و`authenticated`. |
| دوال RPC المحمية تظهر تحذير `SECURITY DEFINER` | متوقع ومراقب | يلزم تنفيذها عبر `authenticated` لأنها نقاط RPC؛ كل دالة تتحقق داخلياً من المستخدم والدور والحالة، وقد ثبت رفض المستخدم العادي والمحظور. |
| Leaked Password Protection معطل في Supabase Auth | متبقٍ | إعداد منصة من لوحة Supabase يجب تفعيله قبل أي حسابات بشرية حقيقية. |

> لا ينبغي وضع Service Role في المتصفح أو Cloudflare Pages العامة. يبقى هذا المفتاح للخدمات الموثوقة من جهة الخادم فقط [2].

## 8. الحدود الصريحة للمرحلة

لم يتم تنفيذ أي Migration لبيانات حقيقية، ولا تحويل الموقع أو استبدال خادم Express/tRPC، ولا ربط Cloudflare Pages، ولا تغيير DNS أو Domain، ولا تغيير Production أو إيقاف الموقع الحالي. لا يصح تفسير نجاح هذا التقرير كتفويض لترحيل Production.

## 9. القرار المقترح للمرحلة التالية

بيئة **Supabase Development** جاهزة كقاعدة اختبار معزولة. قبل أي Migration حقيقي، يلزم موافقة مستقلة على مرحلة جديدة تتضمن: تفعيل حماية كلمات المرور المسربة في Supabase Auth، وتحديد بديل Manus OAuth، وتكامل واجهة المختبر مع Supabase، واعتماد حساب أو نطاق بريد اختبار لإتمام اختبار HTTP/Offline الفعلي، ثم مراجعة منفصلة لخطة Cloudflare Pages. لا ينبغي نقل أي بيانات Production قبل مراجعة نتائج هذه الخطوات ومنح موافقة صريحة جديدة.

## 10. ملحق إغلاق الموانع — 22 أغسطس 2026

> يحل هذا الملحق محل القيود السابقة في الأقسام 5 و7 و9 المتعلقة بعدم وجود واجهة Supabase أو عدم اكتمال اختبار Offline/Online أو نتيجة تدقيق التبعيات.

بعد التقرير الأساسي أضيف مسار واجهة مستقل هو `/migration-lab/supabase` مخصص لـDevelopment. يستخدم هذا المسار مفتاح Supabase العام في المتصفح فقط، ويستدعي جسر tRPC الذي يمرر JWT المستخدم إلى Supabase بحيث تظل RLS هي طبقة القرار الفعلية. يدعم المختبر البحث والإنشاء والتعديل المقيد والأرشفة وتغيير رقم الأرشفة الإداري والسلة والاستعادة، مع إضافة إجراءات RPC وسياسات RLS الخاصة بها.[4](../client/src/pages/SupabaseDevelopmentLab.tsx) [5](../server/routers/supabaseLicenses.ts)

نفذ اختبار Playwright فعلي بحساب مدير اصطناعي مؤكد في Supabase Development. فُصلت شبكة Chromium، ومُلئ نموذج إنشاء حقيقي، وحُفظ العنصر في طابور `localStorage` المستقل للمختبر. بعد إعادة الشبكة، أطلقت الاختبارات حدث `online` لأن Playwright لا يطلقه تلقائياً دائماً، ثم تحققت من ظهور سجل واحد فقط في القاعدة. لذلك أصبح تدفق Offline→Online مثبتاً عبر واجهة المتصفح وطابورها وRPC وIdempotency، من دون حساب بشري أو بيانات Production.[6](../server/supabaseDevelopmentBrowserOffline.integration.test.ts)

كما أضيف اختبار حساب مستخدم عادي اصطناعي يثبت أن قراءة `licenses` تعيد صفراً، والكتابة المباشرة ترفض بـ`42501`، ومحاولة تغيير رقم الأرشفة ترفض بـ`FORBIDDEN`. ويغطي اختبار CRUD الإداري الحساب الاصطناعي والبحث والتعديل والسلة والاستعادة والأرشفة والتدقيق والتجديد وحواجز السجل المؤرشف.[7](../server/supabaseNormalUserRestrictions.integration.test.ts) [8](../server/supabaseDevelopmentCrud.integration.test.ts)

| تحقق محدث | النتيجة |
|---|---|
| TypeScript | ناجح |
| Vitest | **37** ملف اختبار و**104** اختبارات ناجحة |
| بناء الإنتاج | ناجح؛ تحذير حجم الحزمة الرئيسية فقط |
| `pnpm audit --prod` | `No known vulnerabilities found` |
| مستخدم عادي / RLS / RPC | ناجح؛ القراءة والكتابة الإدارية مرفوضتان |
| Offline/Online في المتصفح | ناجح؛ سجل واحد بعد عودة الشبكة |
| Cloudflare read-only | ناجح؛ لا يوجد Pages أو Workers، ولم ينفذ Deploy أو DNS/Domain |

أزيلت الثغرات الحرجة والعالية التي كان يسجلها `pnpm audit --prod`. أدى إصلاح المسار الآمن لـ`path-to-regexp` إلى كشف تعارض مع Express 4، لذلك تمت ترقية Express إلى 5.2.1 وتعديل صيغة wildcard للخادم؛ ثم عاد المسار الجذري المحلي باستجابة `200` واجتازت مجموعة الاختبارات الكاملة.[9](../server/_core/storageProxy.ts) [10](../server/_core/vite.ts)

ما زال مستشار Supabase يعرض تحذير حماية كلمات المرور المسربة وتحذيرات دوال `SECURITY DEFINER`. حسب قرار المستخدم، حماية كلمات المرور المسربة غير متاحة في خطة Supabase Development Free ولا يطلب المشروع ترقية، ولذلك هي خاصية اختيارية موثقة لا مانع مرحلة. أما تحذيرات `SECURITY DEFINER` فمقصودة لدوال الأعمال التي تتحقق داخلياً من الهوية والدور وحالة الاعتماد؛ وقد أثبت اختبار المستخدم العادي عدم إمكان تجاوزها.[11](https://supabase.com/docs/guides/auth/password-security) [12](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)

لا يغير هذا الملحق القرار الحدودي: **لا Publish ولا Cloudflare Deploy ولا Production Migration ولا DNS/Domain ولا نقل بيانات حقيقية**. كما أن صفحات التشغيل القديمة تبقى على MySQL/tRPC؛ المسار الجديد هو مختبر Development معزول، وليس استبدالاً صامتاً للموقع الحالي.
